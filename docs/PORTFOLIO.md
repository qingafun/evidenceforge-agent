# 演示、简历与面试准备

## 五分钟演示路线

1. **0:00–0:40，业务需求**：为一个研发团队设计可恢复、有人工审批的知识库 Agent。展示运行模式，明确离线版是可复现演示。
2. **0:40–1:30，计划与审批**：输入问题，查看研究问题、工具预算、人工审批；说明为什么服务重启不会丢掉待审批任务。
3. **1:30–2:30，工具与证据**：批准后查看执行轨迹，打开一个证据卡并核对原文。解释真实模型如何用 function calling 自主选择工具。
4. **2:30–3:20，报告与边界**：点击引用跳转来源，导出 Markdown；说明“引用有效”与“事实正确”的区别。
5. **3:20–4:10，记忆与资料**：导入一篇自己的 Markdown，保存一个研发偏好，说明下次任务如何使用它，也能主动删除。
6. **4:10–5:00，评测与取舍**：展示 BM25 与 hybrid 实测持平，以及失败样例；介绍下一步如何使用独立数据评估语义检索。

真实模型接入后再录制“自主研究”演示，记录服务商、模型名、日期和输入。不要用离线模板视频暗示真实模型行为。

## 简历写法示例

**EvidenceForge｜可追溯技术调研 Agent 工作台**

Python · FastAPI · LangGraph · SQLite · RAG · MCP

- 构建 Planner–Researcher–Analyst–Critic 研究工作流，在 Researcher 内实现兼容模型的 function calling 循环，结合结构化计划、工具预算和有界修订生成带证据引用的报告。
- 实现 SQLite 检查点、人工审批与服务重启恢复；集成知识检索、来源读取、受限计算器、偏好记忆及 MCP stdio 服务，通过 SSE 展示节点与工具执行轨迹。
- 实现 BM25 + 字符 TF-IDF + RRF 检索，并建立 20 条固定标注用例：两种方案 Recall@5 均为 0.95、MRR@5 均为 0.925；保留失败样例，补充工具边界、恢复、HTTP 与 MCP 集成测试。

这些描述是代码的已实现能力，不是你已经有企业生产经验的证明。建议在你完整阅读、能现场修改并解释源码以后再使用；可以根据实际参与情况表述为“在 AI 工具辅助下设计、实现与验证”。不要声称独立从零手写了并未亲自完成的所有代码。

## 面试必须能解释的八个问题

| 问题 | 可沿着代码解释的要点 |
|---|---|
| 和固定工作流有什么区别？ | 外层确定性图控制生命周期；内层真实 Researcher 自主选工具与参数；离线模式是规则驱动 |
| 为什么使用 LangGraph？ | 显式状态、条件路由、interrupt 与持久检查点；也说明单进程 SQLite 的限制 |
| 重启为什么不会重复执行所有步骤？ | 同 thread_id 加载节点边界；已完成节点跳过，失败节点重做；不是 exactly-once |
| 怎么控制死循环和成本？ | 工具步数、图递归上限、一次修订、HTTP 超时、有限重试、累计预算和估算标记 |
| 混合检索为什么没提升？ | 小型自建语料与词法相似方法重叠；看失败例与分项结果，不能为漂亮指标调测试集 |
| 如何避免幻觉？ | 证据约束、有效引用检查、Critic、证据不足提示；这只能降低风险，不能保证所有事实 |
| 如何应对提示注入？ | 文档是非可信数据；模型外的工具白名单、schema、无任意代码和任意URL抓取；保留残余风险 |
| MCP 和普通函数调用有何不同？ | 内部工具函数服务应用；MCP 把工具/资源通过标准协议暴露给外部客户端，本项目测试真实握手 |

## 你可以亲自完成的下一轮迭代

**第一阶段：接入并记录真实模型。** 用 10 个真实研究问题跑全流程，人工标注事实支持程度、可执行建议与失败原因；记录用量和耗时，输出模型评测报告。代码测试通过不能替代这一步。

**第二阶段：设计检索实验。** 增加独立资料和 50 条以上标注查询，尤其补充中英文语义转述、数字条件和否定条件。比较 BM25、当前 hybrid、神经 embedding 及 reranker；固定数据集后再调参数，防止泄漏。

**第三阶段：选择一个工程深挖点。** 例如把任务搬到持久队列并验证 worker 崩溃恢复，或实现基于来源可信度的证据评分。先描述故障场景和验收指标，再实现，面试更容易讲清楚价值。

不要写“提效 80%”“支持百万文档”“生产级”“完全杜绝幻觉”等未被实验支持的结论。这里没有训练或微调经验，相关岗位应另补训练、推理优化或模型评测项目。
